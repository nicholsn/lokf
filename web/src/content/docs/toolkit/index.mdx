The `lokf` Python package is the toolkit around the format: everything you
need to **load** a bundle, **inspect** the vocabulary, **project** markdown to
RDF, **query** it with SPARQL, **serve** it locally, **propose** typed
relations from prose links, and **export** the result as a graph or as
schema.org JSON-LD. It also **federates** bundles through a [registry](/toolkit/registry/).
It includes [CLI commands and options](/reference/cli/), a [bundle MCP server](/toolkit/mcp/), and a [registry MCP server](/toolkit/registry/). The CLI's commands are `lokf new`, `validate`, `convert`, `query`,
`serve`, `propose`, `vocab`, `adapt`, `tables`, `export`, `registry`, `skills`
and `mcp`.
The format itself stays where it belongs — in `lokf.yaml`
and the [specification](/specification/); the toolkit never hardcodes a
type or predicate it can read from the schema.

| Module | What it gives you |
|---|---|
| `lokf.model` | `load_bundle()` → `Bundle` / `Concept` objects, JSON-LD and `rdflib.Graph` projection |
| `lokf.rdf` | `serialize()` / `graph_of()` — project markdown to RDF ([`lokf convert`](/toolkit/convert/)) |
| `lokf.store` | `GraphStore` — an in-memory pyoxigraph store for SPARQL ([`lokf query`](/toolkit/query/)) |
| `lokf.server` | `serve()` — a local SPARQL endpoint + graph explorer ([`lokf serve`](/toolkit/serve/)) |
| `lokf.schema` | `vocabulary()` → the typed-relation slots and `RelationType` vocabulary, straight from `lokf.yaml` |
| `lokf.adapt` | `adapt()` — a published LinkML schema as a [domain vocabulary](/guide/domain-vocabularies/) ([`lokf adapt`](/toolkit/adapt/)) |
| `lokf.parse` | frontmatter parsing helpers (`parse_concept`, `isoify`) |
| `lokf.propose` | heuristic [relation proposer](/toolkit/proposer/) + the `lokf propose` CLI |
| `lokf.export` | Cytoscape.js graph elements and schema.org `Dataset` JSON-LD; `lokf export` writes the four files a [registry](/toolkit/registry/) harvests |
| `lokf.schema_docs` | `schema_documentation()` resolves classes, effective slots, and other definitions for the [schema browser](/toolkit/scaffold/#browse-the-schema) |
| `lokf.views` | `compile_views()` follows declared paths to generate [navigation views](/reference/declarative-views/) |
| `lokf.tables` | `to_frames()` and writers for CSV, Parquet, and SQLite |
| `lokf.registry_mcp` | the `lokf registry mcp` server for browsing and querying a federated registry |
| `lokf.registry` | `Registry`: a manifest of bundles, each in its own named graph ([`lokf registry`](/toolkit/registry/)) |
| `lokf.mcp_server` | the `lokf mcp` / `lokf-mcp` [MCP server](/toolkit/mcp/) that exposes the toolkit to agents |
| `lokf.build` | the `lokf-build` console script that regenerates every artifact |

## Install

Installing `lokf` gives you the CLI (`lokf`), the [MCP server](/toolkit/mcp/)
(`lokf-mcp`), and the bundled [agent skills](/toolkit/agents/):

<Tabs>
  <TabItem label="uv">

    ```bash
    uv pip install lokf
    ```

  </TabItem>
  <TabItem label="pip">

    ```bash
    pip install lokf
    ```

  </TabItem>
</Tabs>

The core package can load, query, and serve a bundle using the built-in
vocabulary. Install the `build` extra to work with domain vocabularies,
validate bundles, or regenerate schema artifacts:

```bash
uv pip install 'lokf[build]'
```

The `shacl` extra adds SHACL validation, and the `tables` extra adds the
DataFrame and tabular export dependencies.

`lokf --version` (or `lokf -V`) prints the installed version — a quick check
that the CLI is on your `PATH`.

Working inside a clone of this repository? `uv sync` already installs the
package (with the `build` extra) in editable mode — see
[Getting started](/getting-started/).

## A five-minute tour

Everything below runs against the committed
[reference bundle](/examples/), from the repository root:

```python
import lokf

# Load a bundle: a directory of markdown files, nothing else.
bundle = lokf.load_bundle("examples/acme-knowledge")
len(bundle.concepts)        # -> 8
bundle.base_iri             # -> 'https://acme.example/knowledge/'

# Concepts are addressable by Concept ID, path, or IRI.
wau = bundle.get("metrics/weekly-active-users")
wau.type, wau.title         # -> ('Metric', 'Weekly Active Users')
wau.data["formula"]         # frontmatter is a plain dict (body included)

# The same bundle, as RDF — this is the committed 157-triple projection.
g = bundle.graph()
len(g)                      # -> 157
print(g.serialize(format="turtle"))
```

And the vocabulary side — the typed-relation fields, read from the LinkML
schema rather than hardcoded:

```python
vocab = lokf.vocabulary()

# Inspect the relation a navigation path follows.
"measures" in vocab.relation_slots           # -> True

vocab.relation_slots["derivedFrom"].curie   # -> 'prov:wasDerivedFrom'
vocab.relation_slots["measures"].domains    # -> frozenset({'Metric'})
vocab.expand("prov:wasDerivedFrom")         # -> 'http://www.w3.org/ns/prov#wasDerivedFrom'
```

The same vocabulary is available from the CLI. `lokf vocab` prints the
typed-relation table; `lokf vocab --all` widens it to the whole schema
reference — every class, frontmatter slot and value enum with its own
description — and `--json` emits either as JSON:

```bash
lokf vocab                  # the typed-relation vocabulary
lokf vocab --all --json     # the full reference, machine-readable
lokf vocab --bundle knowledge --all --json --include-metadata  # project model and revision
```

Agents get the same thing from the MCP server's `get_vocabulary` tool, which
accepts `all`, `bundle`, `schema`, and `include_metadata`. An explicit schema takes precedence over project discovery.

:::tip[The schema travels with the package]
`vocabulary()` and `load_context()` resolve `lokf.yaml` and
`lokf.context.jsonld` in this order: an explicit path argument first,
then a checkout found by walking up from the current directory — so
local schema edits always win — and only then the copies packaged
inside the wheel, the fallback that lets an installed `lokf` work
outside a repo checkout.
:::
